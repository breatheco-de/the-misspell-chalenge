# The Misspell Challenge
<!-- endhide -->

Learning in public means collaboration, and you don't have to be an expert to collaborate. Misspells come to the rescue! The perfect ice-breaker for open-source contributions; fixing a misspell is easy and requires almost no GitHub or Git experience.

## 🔷 How to fix a misspell on a 4Geeks Lesson:  

![edit on Github](https://github.com/breatheco-de/the-misspell-chalenge/blob/master/assets/github-logo2.png?raw=true)

1. Click the pencil icon that says "Edit on GitHub" at the top right of the lesson, and the lesson source file will be editable. 

2. Correct the misspelling of the lesson.

3. Finally, click on `"Pull Request"`.

## Ignacio Note

A Pull Request (PR) is a collaborative feature on GitHub (and other Git platforms) that allows a developer to notify team members that they have completed a feature, bug fix, or update in a specific branch.

Think of it as a formal proposal to merge your code into the main project. Instead of just overwriting the main codebase, you are "requesting" that the project maintainers "pull" your changes into the primary branch after they have reviewed them.

Why Pull Requests are Important:

Pull requests are the heart of professional software development because they act as a "quality gate" for code. Here is why they are essential:

* Code Review & Quality Control: PRs provide a dedicated space for peers to read your code, leave comments, and suggest improvements. This helps catch bugs, security vulnerabilities, or logic errors before they reach the final user.

* Knowledge Sharing: They serve as a learning tool. Junior developers can learn from senior feedback, and the whole team stays informed about what parts of the system are changing and why.

* Documentation of "The Why": A good PR includes a description of why a change was made. This creates a historical record that future developers can look back on to understand the reasoning behind specific technical decisions.

* Automated Testing (CI/CD): Most professional teams link PRs to automated tools. When you open a PR, "Bots" can automatically run your code to ensure it doesn't break existing features (Regression Testing) or fail to meet style standards (Linting).

* Conflict Prevention: PRs allow the team to see if two people are working on the same file simultaneously. GitHub will flag "Merge Conflicts," forcing a resolution in the PR stage rather than breaking the main production code.

* Safe Experimentation: Because PRs happen on separate branches, you can propose radical changes without any risk to the stable version of the app. If the idea doesn't work out, you simply close the PR without merging it.
